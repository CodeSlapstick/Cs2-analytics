# CS2 Team Analytics

เว็บแอปวิเคราะห์สมรรถนะทีม Counter-Strike 2 สำหรับโค้ชและนักวิเคราะห์
(SP-404 Senior Project · UTCC STECH)

ไฟล์ `.dem` → parse เอง → PostgreSQL → KPI 5 มิติที่โค้ชตั้งน้ำหนักเอง → แดชบอร์ด

---

## สถานะโปรเจกต์ (จบ Sprint 3)

| ส่วน | สถานะ |
|---|---|
| Parser `.dem` → JSON (Python + awpy) | **ผ่านไฟล์จริงแล้ว 2 แมตช์ 2 แมพ** (de_dust2, de_mirage) |
| ฐานข้อมูล PostgreSQL 10 ตาราง + migration | ใช้งานได้ |
| ETL: JSON → PostgreSQL (idempotent) | ใช้งานได้ + มีเทสต์ |
| คำนวณ KPI รายบุคคลจากฐานข้อมูล | ใช้งานได้ + มีเทสต์ |
| REST API | ใช้งานได้ |
| Frontend: layout, navigation, กราฟ ECharts | ใช้งานได้ |
| Frontend ต่อ API จริง (ไม่มีข้อมูลสุ่มแล้ว) | ใช้งานได้ |
| Map analytics: แบ่งโซนด้วย unsupervised ML + ให้คะแนน | ใช้งานได้ + มีเทสต์ |
| หน้าอัปโหลด `.dem` ในเว็บ | ใช้งานได้ (ทดสอบกับไฟล์ 297 MB แล้ว) |

**pipeline เดินครบเส้นด้วยข้อมูลจริงแล้ว 2 แมตช์ 2 แมพ**

| แมตช์ | แมพ | รอบ | ขนาดไฟล์ | เข้าระบบทาง |
|---|---|---|---|---|
| FaZe vs Spirit | de_dust2 | 19 (13:6) | 297 MB | คอมมานด์ไลน์ |
| FURIA vs Falcons | de_mirage | 21 (8:13) | 438 MB | **หน้าอัปโหลดในเว็บ** |

สกอร์บอร์ดของแมตช์แรก K/D รวม 128/128 สมดุลกัน และสกอร์ตรงกับผลจริง

การลองกับไฟล์จริงเจอบั๊กสองตัวที่ข้อมูลจำลองจับไม่ได้ (แก้แล้ว ดู Changelog):
ADR เฟ้อ 39% เพราะนับดาเมจแบบ overkill และยอดยูทิลิตี้เฟ้อเท่าตัวเพราะนับ
ระเบิดที่ยังถืออยู่ในมือรวมกับลูกที่ขว้างออกไปจริง

ฐานข้อมูลตอนนี้มีทั้งแมตช์จริง 1 แมตช์และแมตช์จำลองจาก `npm run db:seed` อีก 12 แมตช์
(`source` ในตาราง `matches` แยกไว้: `demo` = ของจริง, `sample` = ของจำลอง)

```

    │
    │  parser/parse_demo.py            (Python + awpy — ดึงข้อเท็จจริงดิบอย่างเดียว)
    ▼
 normalized JSON                       (สัญญาข้อมูลกลาง — docs/normalized-match.md)
    │                                   ▲
    │  backend/src/etl/                 │ backend/db/seed.js สร้างรูปแบบเดียวกัน
    │    ├─ derive.js  คิด opening/trade/clutch/ADR/KPI  ← สูตรทั้งหมดอยู่ที่เดียว
    │    └─ load.js    เขียนลง DB ใน transaction เดียว
    ▼
 PostgreSQL  (10 ตาราง: users, teams, team_members, coach_notes,
    │                    players, matches, rounds, match_players, events, player_match_kpi)
    │  backend/src/services/analytics.js
    ▼
 REST API (Express) ──► React + Vite + ECharts
```

**หลักการที่ยึดไว้:** parser ส่งแค่ "ใครฆ่าใคร ตอนไหน ตรงไหน" ส่วนสูตรทั้งหมด
(opening duel, trade, clutch, ADR, KPI) อยู่ใน `backend/src/etl/derive.js` **ที่เดียว**
ข้อมูลจำลองกับข้อมูลจริงจึงเดินผ่านโค้ดคำนวณชุดเดียวกัน ไม่มีทางที่ตัวเลขสองทางจะเพี้ยนกัน

## ติดตั้งและรัน

ต้องมี **Node.js 22.13 ขึ้นไป** (`node -v`) และ **Python 3.11 ขึ้นไป** ถ้าจะใช้ parser

```bash
# 1) ติดตั้ง dependency
npm run setup

# 2) ตั้งค่า env
cp backend/.env.example backend/.env      # แก้ JWT_SECRET เป็นค่าสุ่มของตัวเอง

# 3) สร้างฐานข้อมูล + ใส่ข้อมูลตัวอย่าง
npm run db:setup

# 4) รัน (สองเทอร์มินัล)
npm run dev:backend      # http://localhost:4000
npm run dev:frontend     # http://localhost:5173
```

เปิด **http://localhost:5173** → กล่อง "โหมดทดสอบ" ใส่ Steam64
`76561198283431555` (เติมไว้ให้แล้ว) จะเห็นข้อมูลตัวอย่างครบทุกหน้า

### ฐานข้อมูล: ไม่ต้องลง PostgreSQL ก็รันได้

| ตั้ง `DATABASE_URL` ใน `.env` | ได้อะไร |
|---|---|
| **ไม่ตั้ง** (ค่าเริ่มต้น) | ใช้ **PGlite** — PostgreSQL 18 ที่คอมไพล์เป็น WebAssembly รันในโปรเซส Node เก็บไฟล์ที่ `backend/data/pgdata` ไม่ต้องลงอะไรเพิ่ม |
| **ตั้ง** เช่น `postgres://cs2:cs2@localhost:5433/cs2_analytics` | ต่อ PostgreSQL server จริง เปิดได้ด้วย `docker compose up -d db` |

เป็น Postgres จริงทั้งคู่ (`SELECT version()` ของ PGlite ตอบ `PostgreSQL 18.3 … on wasm32`)
migration/SQL/jsonb ชุดเดียวกันใช้ได้ทั้งสองทาง เหตุผลเดียวกับที่ Sprint 0 เลือก
`node:sqlite` แทน `better-sqlite3` คือคนในทีมและกรรมการต้องรันได้โดยไม่ต้องลง
เซิร์ฟเวอร์ก่อน แต่คราวนี้ไม่ต้องแลกด้วยการเปลี่ยนภาษา SQL

> ⚠️ **PGlite เปิดไฟล์ฐานข้อมูลได้ทีละโปรเซสเท่านั้น** — ต้องปิด backend ก่อนรัน
> `db:migrate` / `db:seed` / `etl` ไม่งั้นข้อมูลจะเพี้ยน (เจอมาแล้วตอนพัฒนา sprint นี้)
> ถ้าต้องรันพร้อมกันบ่อย ๆ ให้ย้ายไปใช้ Postgres จริงผ่าน docker compose

## ทำงานกับไฟล์ .dem จริง

```bash
pip install -r parser/requirements.txt

# 1) แปลงไฟล์ (ดูสรุปก่อนว่าอ่านได้ครบไหม)
python parser/parse_demo.py match.dem --summary

# 2) เขียนเป็น JSON
python parser/parse_demo.py match.dem -o backend/data/matches/

# 3) โหลดเข้าฐานข้อมูล (ปิด backend ก่อนถ้าใช้ PGlite)
npm run etl -- data/matches

# 4) แบ่งโซนของแมพนั้นใหม่ ให้ Map analytics รวมแมตช์นี้ด้วย
python parser/map_zones.py de_dust2
```

หรือจะ **ลากไฟล์มาวางในหน้า "อัปโหลด .dem"** ก็ได้ — ทำขั้นที่ 2, 3, 4 ให้ครบอัตโนมัติ
แล้วมีปุ่มพาไปดูผลวิเคราะห์พื้นที่ของแมพนั้นต่อได้เลย

การ fit โซนใหม่ทุกครั้งที่อัปโหลดมีผลข้างเคียงที่ต้องรู้: **ขอบเขตโซนขยับได้**
ตัวเลขที่จดไว้สัปดาห์ก่อนจึงอาจไม่ตรงกับที่เห็นวันนี้ ไฟล์โซนจึงบันทึก `fit_from` ไว้เสมอ
ว่ามาจากกี่แมตช์ไหนบ้าง ย้อนตรวจได้ว่าตัวเลขชุดไหนมาจากข้อมูลชุดไหน
· ถ้าแบ่งโซนไม่สำเร็จ (เช่นแมพใหม่ที่จุดตายยังไม่พอ) แมตช์ยังเข้าฐานข้อมูลตามปกติ
แค่รายงานเป็นคำเตือน ไม่ทำให้ทั้งงานล้มเหลว

โหลดไฟล์เดิมซ้ำได้ไม่จำกัด — ระบบใช้ `external_id` ที่คำนวณจาก **เนื้อไฟล์**
(ไม่ใช่ชื่อไฟล์) เป็นตัวกัน ผลคืออัปเดตทับของเดิม ไม่ใช่ข้อมูลซ้อน
และ **โน้ตของโค้ชไม่หาย** เพราะไม่ได้เป็นผลจากการ parse

รายละเอียดเพิ่มเติมของ parser อยู่ใน [`parser/README.md`](parser/README.md)
รูปแบบ JSON กลางอยู่ใน [`docs/normalized-match.md`](docs/normalized-match.md)

## KPI 5 มิติ คิดยังไง

โค้ดอยู่ใน `backend/src/lib/kpi.js` (ฟังก์ชันบริสุทธิ์ทั้งไฟล์ เขียนเทสต์ยิงตรงได้)

| มิติ | คิดจาก |
|---|---|
| **aim** | ADR (ดาเมจต่อรอบ), สัดส่วนเฮดช็อต, คิลต่อรอบ |
| **positioning** | การตายต่อรอบ, อัตรารอดจนจบรอบ, ตายในจุดที่เพื่อนล้างแค้นให้ได้ทัน |
| **utility** | ดาเมจจากระเบิดต่อรอบ, แฟลชแอสซิสต์, จำนวนยูทิลิตี้ที่ใช้ |
| **clutch** | อัตราชนะ 1vX และความถี่ที่ต้องเจอสถานการณ์นั้น |
| **opening** | อัตราชนะการดวลคู่แรกของรอบ, ความถี่ที่กล้าเปิดไฟต์ |

แต่ละตัวชี้วัดเทียบกับ **ค่าฐาน** (center + spread) ที่ประกาศไว้ใน `KPI_BASELINES`
แล้วแปลงเป็นสเกล **−10 ถึง +10** โดย 0 = ผู้เล่นระดับกลาง ตัดที่ ±2.5 ช่วงเบี่ยงเบน
เพื่อไม่ให้แมตช์เดียวที่โหดผิดปกติดึงคะแนนรวมจนเพี้ยน

สองเรื่องที่ตั้งใจออกแบบให้ต่างจากที่คนทั่วไปทำ:

1. **"ไม่มีข้อมูล" ≠ "ทำได้แย่"** — ผู้เล่นที่ไม่เคยเจอสถานการณ์ 1vX เลย มิติ clutch
   จะเป็น `null` (ขึ้นเป็น "—") ไม่ใช่ 0 หรือติดลบ และน้ำหนักของตัวชี้วัดที่เหลือ
   จะถูกเกลี่ยใหม่อัตโนมัติ
2. **โค้ชตั้งน้ำหนักเองได้ 0–5 ต่อมิติ** (หน้า "ทีม") ทีมที่เล่นช้าเน้นยูทิลิตี้
   กับทีมที่เน้นบุกเปิดไฟต์ ไม่ควรถูกวัดด้วยไม้บรรทัดอันเดียวกัน — ให้น้ำหนัก 0
   คือตัดมิตินั้นออกจากคะแนนรวมไปเลย

คะแนน KPI รายแมตช์ถูกคำนวณตอน ETL แล้วเก็บลงตาราง `player_match_kpi` พร้อม
`metrics` ดิบใน jsonb เพื่อให้ย้อนตรวจได้ว่าคะแนนมาจากตัวเลขอะไร
ส่วนคะแนน "ตลอดกาล" คิดจากผลรวมทุกแมตช์แล้วเข้าสูตรครั้งเดียว (ไม่ใช่เอาคะแนน
รายแมตช์มาเฉลี่ย) เพราะแมตช์ที่เล่น 8 รอบกับ 24 รอบไม่ควรมีน้ำหนักเท่ากัน

## วิเคราะห์พื้นที่ในแมพ (Map analytics)

ตอบคำถามที่สกอร์บอร์ดตอบไม่ได้: **"ทีมเราแพ้ตรงไหนของแมพ"** เพราะสกอร์บอร์ด
ยุบทั้งแมพเหลือตัวเลขเดียว

### แบ่งโซนยังไง

วิธีที่ตรงไปตรงมาที่สุดคือตีกริดสี่เหลี่ยมทับแมพ แต่กริดไม่รู้จักแมพ เส้นกริดจึง
ผ่ากลางจุดที่คนปะทะกันจริงบ่อย ๆ ทำให้จุดปะทะจุดเดียวถูกหั่นไปอยู่คนละช่อง
ตัวเลขที่ได้ก็เลยแปลไม่ออก

`parser/map_zones.py` จึงให้ **ข้อมูลบอกเองว่าโซนอยู่ตรงไหน**:

| ขั้น | ทำอะไร | ทำไม |
|---|---|---|
| จับกลุ่ม | **KMeans** บนพิกัดที่มีคนตายจริง | บังคับให้ทุกจุดสังกัดโซน จึงแบ่งพื้นที่ได้ครบทั้งแมพ |
| เลือกจำนวนโซน | **silhouette score** สูงสุด | ให้ตัวเลขเดียวเทียบกันตรง ๆ ต่างจาก elbow ที่ต้องใช้ตาคนอ่าน |
| หา hotspot | **DBSCAN** ในแต่ละโซน | ทิ้งจุดกระจัดกระจายเป็น noise ได้ เหลือเฉพาะจุดที่คนตายซ้ำจริง |
| ตั้งชื่อโซน | callout ในเกมที่พบบ่อยสุดในกลุ่ม | ติดป้าย**หลัง**จับกลุ่มเสร็จ ไม่ได้ใช้ตอนจับกลุ่ม (ไม่งั้นไม่ใช่ unsupervised) |

มีเงื่อนไขเพิ่มว่า **ทุกโซนต้องมีจุดอย่างน้อย 15 จุด** เพราะ silhouette สนใจแค่รูปทรง
ของกลุ่ม ไม่สนว่ากลุ่มนั้นมีข้อมูลพอจะคิดสถิติไหม ปล่อยไว้จะได้ k สูง ๆ ที่สวยบนกระดาษ
แต่มีโซนละ 3 คิล ซึ่งเอาไปสรุปอะไรไม่ได้

**เทียบกับ baseline เสมอ** ทุกครั้งที่ fit จะคำนวณ silhouette ของกริดตายตัวที่มีจำนวนช่อง
ใกล้เคียงกันไว้ด้วย ถ้า ML ไม่ชนะกริด หน้าเว็บจะขึ้นเตือนว่ายังไม่ควรเชื่อโซนชุดนี้
(ผลจาก de_dust2 แมตช์แรก: KMeans **0.4515** vs กริด **0.3774**)

### ให้คะแนนโซนยังไง

คะแนนอยู่ในช่วง −10..+10 สเกลเดียวกับ KPI 5 มิติ เพื่อให้โค้ชอ่านด้วยความรู้สึกเดียวกัน

```
คะแนน = (สัดส่วนคิลของทีมนั้นในโซน − 0.5) × 20
สัดส่วน = (คิล + 2) / (คิล + ตาย + 4)
```

ใช้**สัดส่วน**ไม่ใช่**ผลต่าง** เพราะโซนที่ปะทะกัน 40 ครั้งกับ 8 ครั้ง ผลต่าง +4 เท่ากัน
แต่ความหมายต่างกันมาก ส่วน `+2 / +4` คือ pseudo-count กันโซนที่ปะทะครั้งเดียวแล้วชนะ
ไม่ให้เด้งไป +10 ทันที — ยิ่งข้อมูลน้อย คะแนนยิ่งถูกดึงกลับเข้าใกล้ 0

### กริด กับ โซน — สองชั้นที่ตอบคนละคำถาม

หน้าเว็บวางข้อมูลสองชั้นทับภาพแมพ เปิด/ปิดได้อิสระ

| ชั้น | ตอบคำถาม | ลักษณะ |
|---|---|---|
| **กริด** | "ตรงพิกัดนี้เกิดอะไรขึ้น" | ช่องสี่เหลี่ยมขนาดเท่ากันทั้งแมพ (300 หน่วยเกม ≈ 5.7 ม.) เรียกชื่อช่องได้ เช่น `K4` |
| **โซน** | "พื้นที่นี้เรียกว่าอะไร ใครคุมอยู่" | มาจาก KMeans หยาบกว่า แต่มีชื่อและความหมายเชิงยุทธวิธี |

กริดยึดมุมบนซ้ายของภาพเรดาร์เป็นจุดตั้งต้น เส้นกริดจึงตรงกับขอบพิกเซลเสมอ และช่อง
`K4` บนจอกับในไฟล์ JSON เป็นช่องเดียวกันแน่นอน

ในช่องกริด **สีบอกว่าใครได้เปรียบ ส่วนความทึบบอกว่ามีข้อมูลมากแค่ไหน** — คนละตัวแปรกัน
ช่องที่มีคิลเดียวจึงจางจนไม่ตะโกน แม้คะแนนจะสุดขั้ว

ลูกศรทิศทางการยิงปิดไว้เป็นค่าเริ่มต้น เพราะเปิดพร้อมกันหลายเส้นแล้วอ่านไม่ออก
ข้อมูลเดียวกันอยู่ในตาราง "เส้นทางการปะทะ" ใต้แผนที่

### ข้อสรุปเชิงลึก — จากตัวเลขไปเป็นสิ่งที่เอาไปซ้อมได้

ตัวเลขพื้นที่บอกว่า "ตรงนี้ใครได้เปรียบ" ซึ่งยังไม่ตอบว่า **"แล้วต้องแก้อะไร"**
`backend/src/services/mapInsights.js` เดินต่ออีกก้าว ตอบสามคำถาม

**1. แยกฝั่ง T / CT** — แผนของโค้ชคนละแผนกันสองฝั่ง ตัวเลขที่รวมสองฝั่งไว้ด้วยกัน
ดูดีแต่เอาไปวางแผนไม่ได้ · ฝั่งของแต่ละรอบอนุมานจาก `winner_team_number` + `winner_side`
ของรอบนั้น ไม่ได้คำนวณจากกติกาสลับฝั่ง จึงไม่เพี้ยนเมื่อมี overtime

**2. พื้นที่ไหนชี้ผลรอบ** — ตายเยอะไม่เท่ากับสำคัญ วัดจาก "รอบที่ได้คิลแรกในพื้นที่นี้
จบลงยังไง" เทียบกับอัตราชนะปกติของทีม ใช้คิลแรกเพราะเป็นเหตุการณ์ที่เกิดก่อนทุกอย่าง
จึงตีความว่าเป็นต้นเหตุได้ ไม่ใช่ผลพลอยได้ของการที่ทีมกำลังจะชนะรอบอยู่แล้ว

**3. รายผู้เล่น × พื้นที่** — K/D บอกว่าใครเล่นดี แต่ไม่บอกว่าต้องแก้ตรงไหน
ตาราง "ทีมและผู้เล่น" จึงมีคอลัมน์ *ทำคิลมากสุดที่* กับ *ตายบ่อยสุดที่* ซึ่งเอาไปคุย
กับคนคนนั้นได้ตรง ๆ · แสดงทั้งสองทีมเพราะโค้ชต้องส่องคู่แข่งด้วย ไม่ใช่แค่ทีมตัวเอง

ตัวอย่างข้อสรุปจริงจากแมตช์ที่วิเคราะห์ (ตอนเล่นฝั่ง T):

> รอบที่ได้คิลแรก ชนะ 100% (6/6 รอบ) เทียบกับอัตราชนะปกติ 58% — ต่างกัน +42 จุด

**ไม่สรุปดีกว่าสรุปมั่ว** ข้อสรุปจะถูกสร้างก็ต่อเมื่อผ่านเกณฑ์ขนาดกลุ่มตัวอย่าง
(6 รอบ) เช่นฝั่ง CT ของแมตช์นี้มีแค่ 7 รอบ ระบบจึงไม่สรุปให้เลย
ตัวเลขยังแสดงในตารางแต่แถวถูกทำให้จางพร้อมป้าย "ข้อมูลน้อย" — โค้ชควรเห็นว่ามีข้อมูลอะไรอยู่
แค่ต้องรู้ว่ายังเชื่อไม่ได้

⚠️ นิยาม trade อยู่ที่ `matchTrades()` ใน `etl/derive.js` **ที่เดียว** ทั้งสกอร์บอร์ด
และหน้าแมพเรียกฟังก์ชันตัวเดียวกัน ตอนแรกเขียนแยกกันแล้วได้คำตอบต่างกัน (13 กับ 10
จากข้อมูลชุดเดียวกัน) เพราะฝั่งหนึ่งไม่ได้จับคู่แบบหนึ่งต่อหนึ่ง มีเทสต์ 8 ข้อล็อกไว้แล้ว

### ภาพเรดาร์กับการปรับเทียบพิกัด

พิกัดในไฟล์ `.dem` เป็นหน่วยเกม (ExtendedA อยู่ที่ `145, 2254`) ส่วนภาพเรดาร์เป็นพิกเซล

`scale` (หนึ่งพิกเซลเท่ากับกี่หน่วยเกม) เก็บไว้ที่ **`backend/data/radars.json`
ที่เดียว** — backend ส่งต่อให้หน้าเว็บผ่าน API และสคริปต์ตรวจก็อ่านไฟล์เดียวกัน
(ถ้าเขียนสองที่แล้วแก้ข้างเดียว จุดจะไปตกผิดที่โดยที่หน้าเว็บยังดูปกติทุกอย่าง)

ค่าพวกนี้ผิดแล้วจับยาก เพราะหน้าเว็บยังดูปกติทุกอย่าง แค่จุดไปตกผิดที่ จึงมีเครื่องมือ

```bash
python parser/check_radar_calibration.py de_dust2 --upscale 4
```

มันวาดจุดที่มีคนตายจริงทับภาพเรดาร์ ระบายสีตาม callout ในเกม แล้วให้เราดูว่าจุดที่

ตกตรงตาม callout ทุกจุด** (BombsiteB ลงไซต์ B, BombsiteA ลงไซต์ A, Middle ลงกลางแมพ)

ค่าของ de_dust2 ที่ใช้อยู่ไม่ได้มาจากเอกสาร แต่**หาจากข้อมูลเอง**: ค้นหา
`(scale, pos_x, pos_y)` ที่ทำให้จุดตายจริงตกบนพื้นที่เดินได้ของภาพมากที่สุด

### ทำไมขอบโซนเป็นรูปหลายเหลี่ยม ไม่ใช่วงกลม

ขอบที่วาดคือ **Voronoi cell ของ centroid** ซึ่งเป็นขอบเขตที่ KMeans แบ่งไว้จริง และ
เป็นเส้นเดียวกับที่ `nearestZone()` ใช้ตอนคิดคะแนน ถ้าวาดเป็นวงกลม ภาพที่โค้ชเห็น

ทั้งที่จริงทุกจุดบนแมพมีโซนสังกัดเสมอ

### แบ่งงานเหมือนที่เหลือของระบบ

```
parser/map_zones.py            ออกแบบโซน (ML)     -> backend/data/zones/<map>.json
backend/src/services/mapZones.js  ให้คะแนนโซน (จากฐานข้อมูล)
```

เหตุผลเดียวกับที่ `parse_demo.py` ไม่คิด KPI แต่ปล่อยให้ `derive.js` คิด — และเพิ่มอีกข้อ
คือ **ขอบเขตโซนต้องนิ่ง** ถ้าคำนวณใหม่ทุกครั้งที่เปิดหน้าเว็บ โค้ชจะเทียบตัวเลข
ข้ามสัปดาห์ไม่ได้เลยเพราะโซนขยับตลอด

```bash
# fit โซนใหม่ (ต้องรันซ้ำเมื่อโหลดแมตช์เพิ่ม ถ้าอยากให้โซนรวมแมตช์ใหม่ด้วย)
python parser/map_zones.py de_dust2
python parser/map_zones.py de_dust2 --summary   # ดูผลเฉย ๆ ไม่เขียนไฟล์
```

เข้าหา 50/50 จนอ่านอะไรไม่ได้ — สถิติจะดูเหมือนว่า "ทุกพื้นที่สูสีหมด" ทั้งที่จริงคือ
เรากำลังวัดตัวสุ่ม ไม่ใช่วัดการเล่น

## Login ด้วย Steam ทำงานยังไง

Steam ใช้ **OpenID 2.0** ไม่ใช่ OAuth ขั้นตอนอยู่ใน `backend/src/services/steam.js`:

1. ผู้ใช้กดปุ่ม → เด้งไป `steamcommunity.com/openid/login` พร้อม `return_to`
2. ผู้ใช้ล็อกอินที่ Steam (รหัสผ่านไม่ผ่านเซิร์ฟเวอร์เราเลย)
3. Steam เด้งกลับมาที่ `/auth/steam/return` พร้อมพารามิเตอร์ `openid.*`
4. **เราส่งพารามิเตอร์ทั้งชุดกลับไปถาม Steam ว่าของจริงไหม** (`mode=check_authentication`)
   ขั้นนี้ห้ามข้าม ถ้าเชื่อ `claimed_id` ตรง ๆ ใครก็ปลอมเป็นคนอื่นได้
5. ได้ Steam64 → บันทึกผู้ใช้ → ออก JWT ใส่ httpOnly cookie → เด้งกลับ frontend

> ตอน deploy จริงต้องแก้ `BACKEND_URL` ใน `.env` ให้เป็นโดเมนจริง ไม่งั้น Steam
> จะเด้งกลับไปที่ localhost

**`npm : ... npm.ps1 cannot be loaded because running scripts is disabled`**
เป็นการตั้งค่าความปลอดภัยของ PowerShell แก้ครั้งเดียวจบ:

```powershell
Set-ExecutionPolicy -Scope CurrentUser -ExecutionPolicy RemoteSigned
```

**ตัวเลขในเว็บไม่ตรงกับที่ seed ไว้ / แมตช์หายไปเฉย ๆ**
มี backend รันค้างอยู่ตอนที่รัน `db:seed` หรือ `etl` — PGlite เปิดได้ทีละโปรเซส
ปิด node ให้หมดแล้วรัน `npm run db:setup` ใหม่

**`python parser/parse_demo.py` พังตอน print ข้อความไทย**
คอนโซล Windows เป็น cp874 — สคริปต์บังคับ UTF-8 ให้แล้ว ถ้ายังเจออยู่ให้รัน
`chcp 65001` ก่อน

**เปิดหน้าแดชบอร์ดแล้วขึ้นว่า "ยังไม่มีแมตช์ของคุณในฐานข้อมูล"**

## Changelog

**Sprint 3 (ล่าสุด) — Map analytics ด้วย unsupervised ML + หน้าอัปโหลด**

1. **`parser/map_zones.py`** — แบ่งแมพเป็นโซนการปะทะด้วย KMeans (เลือก k ด้วย
   silhouette ภายใต้เงื่อนไขว่าทุกโซนต้องมีจุดพอ) + DBSCAN หา hotspot ในแต่ละโซน
   ตั้งชื่อโซนจาก callout ในเกมหลังจับกลุ่มเสร็จ และเทียบกับ baseline กริดตายตัวทุกครั้ง
   ผลลัพธ์เก็บเป็น `backend/data/zones/<map>.json` พร้อมบันทึกว่า fit จากกี่แมตช์
2. **`services/mapZones.js`** — ให้คะแนนได้เปรียบรายโซนจากเหตุการณ์จริงในฐานข้อมูล
   (สัดส่วนคิลถ่วงด้วย pseudo-count) + ลูกศรทิศทางการปะทะระหว่างโซน
   นับเฉพาะแมตช์ `source='demo'` เพราะพิกัดของข้อมูล seed เป็นการสุ่ม
3. **หน้า "วิเคราะห์พื้นที่"** — แผนที่โซนเป็น SVG (สเกล x/y เท่ากัน แมพจึงไม่ยืด),
   สีสองขั้วบอกว่าฝั่งไหนได้เปรียบ, ตารางตัวเลขดิบไว้ตรวจย้อนหลัง
   และแสดงคะแนนโมเดลเทียบ baseline ให้เห็นตรง ๆ ว่าทำไมถึงใช้ ML
4. **หน้า "อัปโหลด .dem"** — ลากไฟล์มาวาง ระบบ parse + โหลดเข้าฐานข้อมูลให้เอง
   ส่งเป็น body ดิบ (ไม่ใช่ multipart) จึง pipe ลงดิสก์ได้โดยไม่ต้องเพิ่ม dependency
   และไม่มีจังหวะที่ไฟล์ 300 MB อยู่ในหน่วยความจำทั้งก้อน · ตอบ `job_id` ทันทีแล้วให้

5. ETL ตอนอัปโหลดเรียก `loadMatch()` ในโปรเซสเดียวกับ API ไม่ spawn `etl/cli.js`
   เพราะ PGlite เปิดไฟล์ฐานข้อมูลได้ทีละโปรเซสเท่านั้น
6. `parse_demo.py` เก็บ callout (`attacker_place`/`victim_place`) ลง `meta` ของ kill event
   และพิมพ์บรรทัด ASCII `OUTPUT_JSON=<path>` ลง stdout ให้โปรแกรมอื่นอ่าน path ต่อได้

**Sprint 2 — ผ่านไฟล์ `.dem` จริงไฟล์แรก**

รันไฟล์จริง (FaZe vs Spirit, de_dust2, 297 MB) ผ่านทั้ง pipeline แล้วเทียบตัวเลข
กับความเป็นจริง เจอบั๊กสองตัวที่ข้อมูลจำลองจับไม่ได้เพราะมันถูก generate มาให้
"ถูกอยู่แล้ว" ทั้งคู่อยู่ที่ชั้นอ่านข้อมูลจาก awpy:

1. **ADR เฟ้อ 39%** — `parse_demo.py` อ่านคอลัมน์ `dmg_health` ซึ่งเป็นดาเมจดิบ
   นับ overkill ด้วย (ยิงคนเหลือ 38 hp ด้วยกระสุนที่ทำ 121 → นับ 121)
   เปลี่ยนไปใช้ `dmg_health_real` = เลือดที่หายจริง ซึ่งเป็นนิยามที่ HLTV/Leetify ใช้
   ผลรวมทั้งแมตช์ 19779 → 14258 ทำให้ ADR เฉลี่ยจาก 104 ลงมาเป็น 75 ตรงกับระดับโปร
2. **ยอดยูทิลิตี้เฟ้อเท่าตัว** — ตาราง `grenades` ของ awpy ปน entity สองแบบ:
   ลูกที่ยัง **ถืออยู่ในมือ** (`CSmokeGrenade` ถูกติดตามทุก tick) กับลูกที่
   **ขว้างออกไปแล้ว** (`CSmokeGrenadeProjectile`) โค้ดเดิม dedup ด้วย
   `(รอบ, entity_id)` ถูกแล้ว แต่ไม่ได้แยกสองแบบนี้ จึงนับได้ 969 ลูก
   (430 ลูกที่ขว้างจริง + 539 ลูกที่แค่ถืออยู่) = 5.1 ลูก/คน/รอบ ซึ่งเป็นไปไม่ได้
   เพราะพกได้สูงสุด 4 ลูก แก้เป็นกรองเฉพาะ `*Projectile` เหลือ 430 ลูก
   = 2.26 ลูก/คน/รอบ พร้อมแปลงชื่อคลาสเป็นชื่อสั้น (`CMolotovProjectile` → `inferno`)
   ให้ตรงกับชื่อที่ `derive.js` ใช้
3. เพิ่มเทสต์ parser 3 ข้อ (รวมเป็น 23) ล็อกพฤติกรรมการกรอง `*Projectile` ไว้
   โดยยังมีทางสำรองสำหรับ awpy รุ่นที่ไม่ได้ตั้งชื่อคลาสแบบนี้

5. `.gitignore` เพิ่ม `*.dem` — ไฟล์ demo ดิบใหญ่หลักร้อย MB ไม่ควรเข้า git

**Sprint 1 — pipeline ข้อมูลจริงทั้งเส้น**

1. `parser/parse_demo.py` — parse `.dem` ด้วย awpy เป็น normalized JSON พร้อมพิกัด X/Y/Z
   (ทนต่อการที่ awpy เปลี่ยนชื่อคอลัมน์ระหว่างเวอร์ชัน) + เทสต์ตรรกะการแปลงข้อมูล
2. ย้าย SQLite → **PostgreSQL** 10 ตารางตาม ER diagram ใน proposal พร้อมตัวรัน migration
   (`npm run db:migrate`) และ seed ที่ป้อนผ่าน ETL ตัวเดียวกับข้อมูลจริง
3. **ETL** `backend/src/etl/` — โหลดซ้ำได้ (idempotent), อยู่ใน transaction เดียว,
   คำนวณ opening duel / trade / clutch / ADR / KPI ที่เดียวจบ
4. **คำนวณ KPI จากฐานข้อมูลจริง** เก็บลง `player_match_kpi` พร้อม metrics ดิบไว้ตรวจย้อนหลัง
5. REST API เขียนใหม่บน PostgreSQL + เส้นทางใหม่ (`/api/overview`, `/api/players`,
   `/api/matches`, `/api/matches/:id/kills`)
6. Frontend: เปลี่ยนเป็น layout แถบข้าง, เพิ่มหน้า "แมตช์", เปลี่ยนกราฟเป็น **ECharts**,
   ต่อ API จริงทุกหน้า แยกสถานะ "ยังไม่มีข้อมูล" ออกจาก "ระบบพัง"
7. ลบ `services/sampleData.js` (ตัวสุ่มตัวเลข) ออกจากระบบ — ไม่มีข้อมูลสุ่มหลงเหลืออีก
8. เพิ่มเทสต์ฝั่ง backend 41 ข้อ (`npm test`) ครอบคลุมสูตร KPI, การคำนวณสถิติ, และ ETL

# Parser service — `.dem` → normalized JSON

ส่วนแรกของ pipeline ข้อมูล แยกเป็นโปรเซส Python ต่างหาก **ไม่ได้ฝังในเว็บแอป**
เพราะไลบรารีที่ parse ไฟล์ demo ของ CS2 ได้ดีที่สุด (`awpy` / `demoparser2`)
อยู่ในฝั่ง Python และการ parse หนึ่งไฟล์กิน RAM หลักร้อย MB — ไม่ควรทำใน
process เดียวกับ API ที่ต้องตอบผู้ใช้

```
.dem ──[parse_demo.py]──> normalized JSON ──[npm run etl]──> PostgreSQL
```

## ติดตั้ง

```bash
pip install -r parser/requirements.txt
```

## ใช้งาน

```bash
# แปลงหนึ่งไฟล์ เขียนผลไปที่โฟลเดอร์ที่ ETL อ่าน
python parser/parse_demo.py match.dem -o backend/data/matches/

# หลายไฟล์รวดเดียว
python parser/parse_demo.py demos/*.dem -o backend/data/matches/

# ดูสรุปก่อนว่า parse ได้ครบไหม (ไม่เขียนไฟล์)
python parser/parse_demo.py match.dem --summary

# แล้วโหลดเข้าฐานข้อมูล
npm run etl -- data/matches
```

ตัวเลือกที่ใช้บ่อย

| ตัวเลือก | ความหมาย |
|---|---|
| `-o, --out` | ไฟล์ปลายทาง หรือโฟลเดอร์ (ถ้าเป็นโฟลเดอร์จะตั้งชื่อไฟล์ตาม `external_id` ให้เอง) |
| `--tickrate` | tickrate ของเซิร์ฟเวอร์ ดีฟอลต์ **64** (Premier/matchmaking) — FACEIT บางเซิร์ฟเวอร์เป็น 128 |
| `--summary` | แสดงสรุปอย่างเดียว ใช้เช็กว่าไฟล์ parse ได้ก่อนโหลดจริง |
| `--pretty` | จัดรูป JSON ให้อ่านง่าย (ไฟล์ใหญ่ขึ้น 2–3 เท่า ใช้ตอนดีบักเท่านั้น) |

## หลักการออกแบบ

**parser ดึงข้อเท็จจริงดิบอย่างเดียว ไม่คำนวณสถิติ**

| ทำที่ parser | ทำที่ ETL (`backend/src/etl/derive.js`) |
|---|---|
| ใครฆ่าใคร tick ไหน พิกัดไหน | opening duel, trade, clutch |
| รอบไหนฝั่งไหนชนะ (แปลงเป็น "ทีม" ให้แล้ว) | ADR, HS%, survival rate |
| ใครขว้างระเบิดอะไรกี่ลูก | KPI 5 มิติ |

เหตุผล: ถ้าปล่อยให้สูตรอยู่สองที่ (Python ตอน parse + Node ตอน seed) วันหนึ่ง
จะมีคนแก้ข้างเดียวแล้วตัวเลขสองทางไม่ตรงกันโดยไม่มีใครรู้ ตอนนี้ `seed.js`
กับไฟล์ `.dem` จริงเดินผ่านโค้ดคำนวณชุดเดียวกันเป๊ะ

## เรื่องที่ต้องรู้ก่อนแก้ไฟล์นี้

**1. ชื่อคอลัมน์ของ awpy เปลี่ยนได้ระหว่างเวอร์ชัน**
โค้ดทุกจุดจึงเรียกผ่าน `col(df, "ชื่อแบบที่1", "ชื่อแบบที่2", …)` แทนการอ้างชื่อตรง ๆ
ถ้าอัปเกรด awpy แล้วบางส่วนหาย ให้เพิ่มชื่อใหม่เข้าไปในรายการ อย่าเปลี่ยนเป็นชื่อเดียวตายตัว

**2. `team_number` ยึดจากฝั่งในรอบแรก ไม่ใช่ฝั่งปัจจุบัน**
CS2 สลับฝั่งตอนครึ่งหลัง (MR12) ถ้ายึดฝั่งปัจจุบัน ผู้เล่นคนเดียวจะกลายเป็นคนละทีม
กลางแมตช์ ระบบทั้งระบบใช้ `2 = ทีมที่เริ่มฝั่ง T`, `3 = ทีมที่เริ่มฝั่ง CT`

**3. การหาว่า "ฝั่งที่ชนะ" คือทีมไหน ใช้ข้อมูลจริงของรอบนั้น**
ไม่ได้คำนวณจากกติกาสลับฝั่ง แต่ดูจาก tick ว่ารอบนั้นผู้เล่นของแต่ละทีมอยู่ฝั่งไหน
(กติกาสลับฝั่งใช้เป็นทางสำรองเมื่อไม่มี tick ของรอบนั้นเท่านั้น) เพราะ overtime
มีกติกาสลับฝั่งคนละแบบ และ demo ที่มีการ restart กลางแมตช์จะทำให้การนับรอบเพี้ยน

**4. `external_id` คำนวณจากเนื้อไฟล์ ไม่ใช่ชื่อไฟล์**
(SHA-1 ของ 2 MB แรก + ขนาดไฟล์) เปลี่ยนชื่อไฟล์แล้วโหลดใหม่จึงไม่กลายเป็นแมตช์ใหม่
ETL จะอัปเดตทับของเดิมให้แทน

**5. หนึ่งระเบิด = หนึ่ง event**
`awpy` คืนเส้นทางการเคลื่อนที่ของระเบิดเป็นหลายสิบแถวต่อลูก โค้ดเก็บเฉพาะแถวแรก
ของแต่ละ `entity_id` ถ้าลืมข้อนี้ตัวเลข "ยูทิลิตี้ที่ใช้" จะเฟ้อขึ้นเป็นสิบเท่า

## เทสต์


ยังไม่มีไฟล์ `.dem` จริงในมือ เทสต์จึงสร้าง polars DataFrame ที่หน้าตาเหมือนผลลัพธ์
ของ awpy ขึ้นมาแทน แล้วตรวจตรรกะการแปลงข้อมูลของเรา (สลับฝั่ง, ตัดบอททิ้ง,
นับระเบิดไม่ซ้ำ) **สิ่งที่เทสต์นี้ยืนยันไม่ได้คือชื่อคอลัมน์จริงของ awpy** —
ต้องรอไฟล์ demo จริงมาลองก่อน ซึ่งเป็นงานข้อแรกของ sprint ถัดไป

## เมื่อได้ไฟล์ .dem จริงมาแล้ว ทำอะไรต่อ

1. `python parser/parse_demo.py ไฟล์.dem --summary` — ดูว่าจำนวนรอบ/ผู้เล่นตรงกับที่เห็นในเกมไหม
2. ถ้ามีคอลัมน์ไหนหาย จะมีข้อความ `!` เตือนขึ้นมา ให้เพิ่มชื่อคอลัมน์ที่ awpy ใช้จริงเข้าไปใน `col(...)`
3. `-o backend/data/matches/` แล้ว `npm run etl -- data/matches`
4. เทียบสกอร์บอร์ดในเว็บกับสกอร์บอร์ดในเกม — K/D/A ต้องตรงกันเป๊ะ ถ้าไม่ตรงแปลว่า
   ยังกรอง event ผิดอยู่ (มักเป็นเรื่อง teamkill หรือรอบ warmup ที่หลุดเข้ามา)

## `map_zones.py` — แบ่งแมพเป็นโซนด้วย unsupervised learning

```bash
python parser/map_zones.py de_dust2 --summary   # ดูผลก่อน ไม่เขียนไฟล์
python parser/map_zones.py de_dust2             # เขียน backend/data/zones/de_dust2.json
python parser/map_zones.py de_dust2 --k 8       # บังคับจำนวนโซน
```

อ่านจาก **ไฟล์ normalized JSON** ไม่ใช่จากฐานข้อมูล — ตั้งใจให้เป็นแบบนี้เพราะ
(1) ไฟล์ JSON มีเฉพาะแมตช์ที่ผ่าน parser จริง ข้อมูลจำลองจาก `db:seed` ที่สุ่มพิกัด
จึงปนเข้ามาไม่ได้ตั้งแต่ต้น (2) รันได้โดยไม่ต้องแตะฐานข้อมูล ซึ่งสำคัญเพราะ PGlite
เปิดได้ทีละโปรเซส ถ้าต้องต่อฐานข้อมูลก็จะต้องปิด backend ก่อนทุกครั้ง

หลักการเดียวกับ `parse_demo.py`: **ไฟล์นี้ออกแบบโซนอย่างเดียว ไม่คำนวณสถิติ**
การให้คะแนนโซนอยู่ที่ `backend/src/services/mapZones.js` ที่เดียว

| ทำที่นี่ (Python + scikit-learn) | ทำที่ `mapZones.js` (Node) |
|---|---|
| โซนอยู่ตรงไหน (KMeans) | โซนไหนใครได้เปรียบ |
| จุดตายซ้ำ ๆ อยู่ตรงไหน (DBSCAN) | ลูกศรทิศทางการปะทะ |
| โซนควรมีกี่โซน (silhouette) | โซนไหนข้อมูลน้อยเกินกว่าจะสรุป |
| โซนนี้ควรเรียกว่าอะไร (callout ที่พบบ่อยสุด) | อาวุธที่ใช้บ่อยในโซน |

### เรื่องที่ต้องรู้ก่อนแก้ไฟล์นี้

**1. `random_state` ถูกตรึงไว้**
KMeans เริ่มจากจุดสุ่ม ถ้าไม่ตรึงจะได้โซนคนละชุดทุกครั้งที่รัน แล้วโค้ชจะเทียบตัวเลข
ข้ามสัปดาห์ไม่ได้

**2. เลือก k จาก silhouette แต่ต้องผ่านเงื่อนไข "ทุกโซนมีจุดพอ" ก่อน**
silhouette สนใจแค่รูปทรงของกลุ่ม ไม่สนว่ากลุ่มนั้นมีข้อมูลพอจะคิดสถิติไหม
ถ้าปล่อยตามคะแนนล้วน ๆ ข้อมูลชุดแรก (128 จุด) จะเลือก k=9 แล้วเหลือโซนใช้ได้แค่ 3 โซน

**3. ชื่อโซนติดทีหลัง ไม่ได้ใช้ตอนจับกลุ่ม**
ตัวจับกลุ่มเห็นแค่พิกัด ถ้าเอาชื่อ callout ไปช่วยแบ่งกลุ่มก็ไม่ใช่ unsupervised แล้ว
และจะกลายเป็นแค่การจัดกลุ่มตามป้ายที่ Valve ตั้งไว้ ซึ่งไม่ได้บอกอะไรใหม่

**4. เทียบกับ baseline ทุกครั้ง**
`grid_baseline_silhouette` คือคะแนนของการตีกริดสี่เหลี่ยมที่มีจำนวนช่องใกล้เคียงกัน
มีไว้ตอบคำถาม "จะใช้ ML ทำไม ตีกริดเอาก็ได้" ถ้าไม่ชนะกริด ก็ควรใช้กริด
